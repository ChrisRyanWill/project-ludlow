# Threat model

**Adversaries:** an employer who wants to learn who signed, infiltrate the campaign, or subpoena the operator; someone who compromises the server or its database, or an operator who is compelled to act against the people using it; a legal demand on the operator or the email provider; a rogue or coerced trustee or officer; a faction inside a union; and, over time, plain financial misconduct.

> **Status: early prototype.** An internal, AI-assisted security review ([details](reviews/2026-09-internal-review-1.md)) found real problems, most now fixed, and several design-level limits that are written down below in plain words. It is **not** an independent audit, and it shares the blind spots of whatever wrote the code. Independent review is still the top priority.

## What the design protects

| Threat | Protection |
|---|---|
| Database dump or subpoena of the campaign system | Reveals that campaigns exist, card counts, timestamps and public keys. Union, employer, and every card field are ciphertext the server has no key for. Deleted cards are zeroed on disk (`secure_delete`). |
| A server that stores and serves data, or a stolen database | It never holds a card key, a trustee key, a vote key, or a grievance key, so it cannot read what was sealed. **A server that actively lies is a different case: see "Key substitution" below.** |
| One rogue trustee | Cannot open cards alone once the committee is complete: any k of n are needed. Only the founder hands out trustee seats, one set of keys cannot fill two seats, and the founder checks each trustee's key words aloud before locking cards to the committee. The founder is still the anchor of trust: see "Founder-only phase". |
| Trustees opening the cards too early | **A release number, set when the campaign is created, is enforced by the server:** it will not hand over the sealed cards until that many cards have been signed and counted (vouched for, and not disavowed or withdrawn). The cards live only on the server, so trustees who hold keys still have nothing to decrypt. Raising the number is free; lowering it takes k trustees agreeing on the same value. Signers and members can see the number. **It is a safety catch against premature or careless release, not proof that that many real people signed:** see "The release count". |
| Leaked or forwarded invite link | Direct links are single-use and auto-vouched; group links expire and their cards only count once the link's creator confirms the signer in person, with a 5-try lockout. Trustees can pause a campaign instantly. Link secrets are removed from the address bar and history once a page has read them. |
| Logs | Only method, route *pattern*, status and duration are ever logged (test-enforced). No bodies, queries, headers, tokens or IPs. |
| Request forgery, replay | Challenge-response signatures are single-use, expire in 2 minutes and name the action and the campaign or member. They do not cover the request body: see "Signatures and encrypted fields". |
| Employer or officer reads member data | Workspace personal fields are encrypted at rest; every look at someone's record, including a full export, is logged where they can see it. Case content is end-to-end encrypted to the people it was sealed to, and working a case takes its key. |
| Vote tampering, learning how someone voted | Ballots are stored with no voter reference or timestamp, and every cast re-shuffles that vote's rows so the order people voted in is not left on disk. The counting key is split among the election committee. **A decision that changes dues, rules or a role is always counted with the key published, so the server recounts it and any member can.** A result counted without the key needs signatures over the same numbers from k different committee members. The server refuses to count if the ballots or receipts do not match the number of members who voted. Votes have a minimum length, nobody can end one early, and nobody can run their own recall. **None of this protects against an operator who runs modified code: see "Votes".** |
| Financial misconduct or a rewritten history | Two-officer approval above a threshold; an immutable ledger (database triggers, including against `INSERT OR REPLACE`); hash chains that each member's browser verifies and **pins per device** (ledger and audit log), so a rewrite of history this device has already seen is caught. |
| Officers entrenching themselves | Petition-forced votes and recalls, defined as bylaws data that only a member vote can change. Nobody grants themselves a role, only members who have joined can hold one, and a role a vote removed comes back only by a vote. |
| Someone looking over a shoulder | Quick exit, neutral tab titles, and workspace sessions that live in memory. **Quick exit only leaves the page:** a member's device keeps their sign-in so they can come back. "Forget this device" removes it. |

## Honest limits

### Keys and the server

- **Key substitution (the most important limit).** The server tells each browser which public keys belong to the trustees, to stewards and to the election committee, and browsers seal to whatever they are given. A server that is compromised, or an operator compelled to cooperate, that hands out keys of its own would receive every card, report, grievance and vote sealed after that, **using the genuine code and without changing a byte of JavaScript, so the `/verify` check cannot see it.** Today's defence is human: trustees read each other's key words aloud and the founder checks them before locking cards. Members who sign a card do **not** verify the trustees' keys. Fixing it needs the roster authenticated by a key the server never sees (an open issue). Until then, "the server cannot read cards" means it cannot read what was already sealed, and cannot read new cards unless it is actively lying.
- **The code is delivered by the server.** A compromised server could send malicious JavaScript. Mitigations: a strict CSP, no third-party code, reproducible builds, the option to self-host, and the `/verify` page. **`/verify` is weaker than it looks:** it downloads `app.js` again to work out its fingerprint, so a server determined to cheat could show that request one file and run another, even for the same visitor. It catches mistakes and casual tampering, not a hostile server. The strongest check is to compare with a fingerprint you built yourself, or one that someone you trust worked out on another device and network. This is the largest known weakness.
- **The release lock is enforced by the server, not by mathematics.** It stops trustees, who hold keys but not the sealed cards. It does **not** stop an operator who can read the database directly, and it binds nothing if the trustees also run the server. Host the server somewhere no trustee controls if you want it to bind them. Once the number is met, any k trustees together can open the cards; the software cannot judge whether that is wise.
- **Hosting.** The host may log IP addresses at the network edge. Rate limits and login challenges are held in memory, so run one instance.
- **The confirmation email.** The law needs it. For that moment the server sees the signer's email and card fields, sends the message, and discards them. The email provider keeps its own delivery logs. Because anyone can start a campaign and sign a card, the route could be abused to send mail to strangers from your server's address: an address receives at most three a day (counted in memory only; nothing about the address is stored) and one campaign can send a limited number a day. Also set a quota with your email provider.

### The release count

- **The number counts cards the system accepted, not real people.** A direct invite makes a card count at once, and direct invites can be made by any trustee and by any vouched member. Someone who wants to push the count up (an employer's plant who joined, or a founder who wants to open early cards) can invite and sign fake cards, and the server, which cannot read them, cannot tell. The lock protects against carelessness and against trustees acting in the open, not against an insider willing to fabricate signers. The filing package refuses to claim a majority the numbers do not show, and trustees see the cards when they open them.
- **Founder-only phase.** A campaign can start with one person. Until every planned trustee has joined, each card is sealed to the founder alone, so one person, or anyone who steals their key file and passphrase, can open them. The lock counts cards, so a founder willing to fabricate cards can also pass it. When the trustees have all joined, the founder re-locks the early cards so that k of n are needed, **but re-locking does not re-key**: the founder already saw every early card's key, and any copy of the database made before the re-lock still holds those cards sealed to the founder's key alone, so the founder's key file (or whoever takes it) opens that copy. Treat the founder's key file as a key to those cards for good. If too few trustees can later cooperate (lost keys), those cards cannot be recovered.
- **The release number is visible to the server.** It is a count (by default a majority of the group), which lets a determined adversary estimate the size of the unit.
- **A secretly hostile vouched member** sees the card count, and can raise it (see above). Anyone with a member link can act as that member.

### Votes

- **Ballots are unlinkable in the stored data, not against an operator who runs modified code.** A ballot is submitted over the member's signed-in session. An operator who has altered the server can record which session sent which encrypted ballot; once the ballot key is published (always the case for a decision that changes dues, rules or roles) that reveals how each person voted. Fixing that needs an anonymous channel (a mix network or blind signatures), which this project does not have. Against an unmodified server, a copy of the database shows no voter reference, no timestamp and, because every cast re-shuffles the rows, no cast order. Backups taken before a cast still hold the earlier layout.
- **What a recount proves.** A member's browser can check that the published counts match the ballots stored on the server, and that the member's own receipt is among the receipts. It cannot detect a ballot that was replaced before the key was published: receipts are random codes, not tied to a ballot. That is deliberate (a receipt that identified a ballot would let people prove how they voted to whoever pressures them), but it means the count is only as trustworthy as the server's ballot table. The server does check the ballots and receipts against the number of members who voted.
- **Key custody.** The ballot key is generated in the browser of whoever opens the vote and is split among the committee; that browser holds the whole key at that moment. "Nobody holds the key" means it is never stored whole.
- **Coercion.** Once the key is published, anyone who kept a copy of their own encrypted ballot, or whose device or connection was watched while voting, can show how they voted. For votes where that matters (a strike authorization, say) the committee can leave the key unpublished; the result then carries k committee signatures instead of a recount.
- **Membership is only as good as the identity checks around it.** Whoever generates the claim links can claim any account not yet claimed, and vote as that member.

### Devices and keys

- **A member's sign-in is kept in the browser.** The member link's secret is stored unencrypted in the browser's local storage so a member can come back. Quick exit does not remove it; "Forget this device" does. Anyone who can use an unlocked device can open that member's page.
- **Key files are cached in browser storage** (encrypted under the passphrase with Argon2id). A generated passphrase is about 46 bits; a chosen one only has to be long, so it can be weak. Someone who takes a phone can try guesses offline. Use a generated passphrase.
- **Signatures and encrypted fields.** Request signatures cover the route and the campaign or member, not the request body, so a party that can alter requests after they are signed (a TLS-terminating proxy, a hostile browser extension) could change what a signed request does. Encrypted database fields are bound to their column, not to their row, so someone who can write the database but does not have the master key could swap encrypted values between rows.
- **A copy of the workspace database** shows, even without the master key: shifts, locations, membership status, who voted (not how), who filed grievances and which article they cited, petition signers, and session times. Names, emails, phones, addresses and job titles are encrypted, and it is readable by the server (it must send mail and print notices), so an attacker who steals both the database and `WORKSPACE_MASTER_KEY` reads it.
- **Without `NODE_ENV=production`** (which `npm start` does not set) the master key is written next to the database. Set it, and set `WORKSPACE_MASTER_KEY`.

### Legal deadlines and content

- **Deadlines are reminders, not legal deadlines.** A case's clock starts when the case is filed and each later step's clock when someone records the step, not from the incident or from the employer's answer, so the app's due dates can be later than the contract's or the law's. Have a person check every date against the contract. (An explicit start date for each step is an open issue.)
- **Legal text is a draft.** Nothing here is legal advice, and no lawyer has reviewed it.
- **Once names go to an employer or an agency they are no longer secret.** The encryption protects the organizing period.

### Smaller points

- **Small unions:** with very few members, counts and shifts are inherently identifying; small-group suppression starts at 5, and a hidden group can sometimes be recovered by subtraction when only one group is hidden.
- The spreadsheet exports neutralise formula injection, and PDFs replace characters the standard fonts cannot draw with `?` (the CSV keeps full Unicode).
- **Not independently audited.**
