# Threat model

**Adversaries:** an employer who wants to learn who signed, infiltrate the campaign, or subpoena the operator; someone who compromises the server or its database, or an operator who is compelled to act against the people using it; a legal demand on the operator or the email provider; a rogue or coerced trustee or officer; a faction inside a union; and, over time, plain financial misconduct.

> **Status: early prototype.** An internal, AI-assisted security review ([details](reviews/2026-09-internal-review-1.md)) found real problems, most now fixed, and several design-level limits that are written down below in plain words. It is **not** an independent audit, and it shares the blind spots of whatever wrote the code. Independent review is still the top priority.

## What the design protects

| Threat | Protection |
|---|---|
| Database dump or subpoena of the campaign system | Reveals that campaigns exist, each committee's size (k of n) and release number, card counts, when each card was signed and whether it was vouched, public keys, and which link each card came from and which card made each link (a who-invited-whom map of unnamed cards). It also keeps the email provider's message id for each confirmation email, which, together with the provider's own records, can identify a signer. Union, employer, and every card field are ciphertext the server has no key for. Deleted cards are zeroed on disk (`secure_delete`). |
| A server that stores and serves data, or a stolen database | It never holds a card key, a trustee key or a grievance key, so it cannot read what was sealed. It holds a vote's key only when the committee publishes it for a recount, and then it can decrypt that vote's ballots, as can anyone (that is the point of publishing it). **A server that actively lies about which keys belong to whom is covered for cards and reports (a founder key check in every invitation, and a roster the founder signs) but not yet for grievances and votes: see "Key substitution" below.** |
| One rogue trustee | Once every trustee has joined, the founder has confirmed the committee (signed its roster) and the early cards have been re-locked to it, any k of n are needed to open the cards; until then the founder alone can (see "Founder-only phase"). Only the founder hands out trustee seats, one set of keys cannot fill two seats, the founder checks each trustee's key words aloud and then signs the committee, and each trustee's dashboard checks that their own key is in what was signed. Any single trustee can raise the release number or pause and un-pause the campaign; lowering the number takes k. The founder is still the anchor of trust: see "Key substitution" and "Founder-only phase". |
| Trustees opening the cards too early | **A release number, set when the campaign is created, is enforced by the server:** it will not hand over the sealed cards until that many cards have been signed and counted (vouched for, and not disavowed or withdrawn). The cards live only on the server, so trustees who hold keys still have nothing to decrypt. Raising the number is free; lowering it takes k trustees agreeing on the same value. Signers and members can see the number. **It is a safety catch against premature or careless release, not proof that that many real people signed:** see "The release count". |
| Leaked or forwarded invite link | Direct links are single-use and auto-vouched; group links expire and their cards only count once the signer is confirmed in person, by the member who made the link or by any trustee, with a 5-try lockout. Any trustee can pause a campaign instantly. On the organizing pages, link secrets are removed from the address bar and the tab's history once the page has read them, but the browser's own history list may still keep the original link. The same is done for workspace claim links. |
| Logs | Only a timestamp, the method, the route *pattern*, status and duration are ever logged, plus a short error code when the server fails (test-enforced). No bodies, queries, headers, tokens or IPs. |
| Request forgery, replay | Trustee actions and the workspace sign-in use challenge-response signatures that are single-use, expire in 2 minutes and name the action and the campaign or member. Signer and member links, and a workspace session after sign-in, are bearer tokens: whoever holds one can use it. A trustee's signature also covers the request body: see "Signatures and encrypted fields". |
| Employer or officer reads member data | Workspace personal fields are encrypted at rest; every look at someone's contact details (the member list, a full export) is logged where they can see it. Names are shown on many screens (roles, cases, votes) without a log entry. Case content is end-to-end encrypted to the people it was sealed to, and working a case takes its key. |
| Vote tampering, learning how someone voted | Ballots are stored with no voter reference or timestamp, and every cast re-shuffles that vote's rows so the order people voted in is not left on disk. The counting key is split among the election committee. **A decision that changes dues, rules or a role is always counted with the key published, so the server recounts it and any member can.** A result counted without the key needs signatures over the same numbers from k different committee members. The server refuses to count if the ballots or receipts do not match the number of members who voted. Votes have a minimum length, nobody can end one early, and nobody can run their own recall. **None of this protects against an operator who runs modified code: see "Votes".** |
| Financial misconduct or a rewritten history | Two-officer approval above a threshold; ledger and audit entries the application cannot change (database triggers, including against `INSERT OR REPLACE`); hash chains that browsers verify and **pin per device**, so a rewrite of history this device has already seen is caught. Every member's browser checks the ledger; the audit log is checked only by officers (only they can read it), in full from its first entry. The triggers stop the application's own SQL, not someone with direct write access to the database file, who can drop them; what catches that is the hash chain and the device pins. |
| Officers entrenching themselves | Petition-forced votes and recalls, defined as bylaws data that only a member vote can change. Nobody grants themselves a role, only members who have joined can hold one, and a role a vote removed comes back only by a vote. |
| Someone looking over a shoulder | Quick exit, neutral tab titles, and workspace sessions that live in memory; locking the workspace or quick exit also ends the session on the server. **Quick exit only leaves the page:** a member's device keeps their sign-in so they can come back. "Forget this device" removes it. |

## Honest limits

### Keys and the server

- **Key substitution: closed for cards and reports, still open for the workspace.** Browsers seal to public keys the server supplies. A server that is compromised, or an operator compelled to cooperate, that handed out keys of its own would receive everything sealed to them, **using the genuine code and without changing a byte of JavaScript, so the `/verify` check cannot see it.** For cards, reports and the founder's re-lock this no longer works: every invitation link carries a check of the founder's keys (in the part of the link the server never sees), and once every trustee has joined the founder signs the committee's roster after checking each trustee's key words in person. A signer's browser refuses a founder whose keys do not match its link, seals only to the founder or to the signed roster, and asks for nothing if they do not check out. The tests alter the server's rows and watch the real, unmodified app refuse ([protocol](PROTOCOL.md), section 1a). What is left:
  - **The founder is the anchor of trust.** A founder who signs a roster with a rogue key has betrayed the people the design protects; only the key-words check at that moment catches it.
  - **The link.** A signer trusts whoever gave them the link to have given them the right one. The signing page shows the founder's key words so they can check with the founder.
  - **The workspace.** Grievances (the chief steward's and stewards' keys) and votes (the election committee's keys and each vote's key) still use keys the server supplies. That is a separate design ([#37](https://github.com/ChrisRyanWill/project-ludlow/issues/37)); until it is done, a lying server could read new grievances and votes.
  - **The code itself** (next bullet): all of this assumes the browser runs the genuine app.
- **The code is delivered by the server.** A compromised server could send malicious JavaScript. Mitigations: a strict CSP, no third-party code, builds designed to be reproducible (a local and a Docker build were byte-identical when last checked; that has not been re-checked since the latest security changes), the option to self-host, and the `/verify` page. **`/verify` is weaker than it looks:** it downloads `app.js` again to work out its fingerprint, so a server determined to cheat could show that request one file and run another, even for the same visitor. It catches mistakes and casual tampering, not a hostile server. The strongest check is to compare with a fingerprint you built yourself, or one that someone you trust worked out on another device and network. This is the largest known weakness.
- **The release lock is enforced by the server, not by mathematics.** It stops trustees, who hold keys but not the sealed cards. It does **not** stop an operator who can read the database directly, and it binds nothing if the trustees also run the server. Host the server somewhere no trustee controls if you want it to bind them. Once the number is met, any k trustees together can open the cards; the software cannot judge whether that is wise.
- **Hosting.** The host may log IP addresses at the network edge. Rate limits and login challenges are held in memory, so run one instance.
- **The confirmation email.** The law needs it. For that moment the server sees the signer's email and card fields, sends the message, and discards them. The email provider keeps its own delivery logs. Because anyone can start a campaign and sign a card, the route could be abused to send mail to strangers from your server's address: one mailbox receives at most three a day (letter case, a `+tag` and, for Gmail, dots do not count as a different mailbox), and one campaign can send at most `CONFIRMATIONS_PER_CAMPAIGN_PER_DAY` (default 2,000) a day, withdrawn cards included. Both counts live in memory only, under a salted hash for addresses, and start again when the server restarts; the address itself is never stored. They slow abuse down rather than stop a determined abuser, so also set a sending quota with your email provider.

### The release count

- **The number counts cards the system accepted, not real people.** A direct invite makes a card count at once, and direct invites can be made by any trustee and by any vouched member. Someone who wants to push the count up (an employer's plant who joined, or a founder who wants to open early cards) can invite and sign fake cards, and the server, which cannot read them, cannot tell. The lock protects against carelessness and against trustees acting in the open, not against an insider willing to fabricate signers. The filing package refuses to claim a majority the numbers do not show, and trustees see the cards when they open them. Trustees can also see where the count comes from (how many cards came from each trustee's invitations, from members' invitations and the most from any one member, and from group links confirmed in person), so one person accounting for much of it shows; that makes inflation visible, not impossible.
- **Founder-only phase.** A campaign can start with one person. Until every planned trustee has joined **and the founder has confirmed the committee**, each card is sealed to the founder alone, so one person, or anyone who steals their key file and passphrase, can open them. The lock counts cards, so a founder willing to fabricate cards can also pass it. When the trustees have all joined, the founder re-locks the early cards so that k of n are needed, **but re-locking does not re-key**: the founder already saw every early card's key, and any copy of the database made before the re-lock still holds those cards sealed to the founder's key alone, so the founder's key file (or whoever takes it) opens that copy. Treat the founder's key file as a key to those cards for good. If too few trustees can later cooperate (lost keys), those cards cannot be recovered.
- **The release number is visible to the server.** It is a count (by default a majority of the group), which lets a determined adversary estimate the size of the unit.
- **A secretly hostile vouched member** sees the card count, and can raise it (see above). Anyone with a member link can act as that member.

### Votes

- **Ballots are unlinkable in the stored data, not against an operator who runs modified code.** A ballot is submitted over the member's signed-in session. An operator who has altered the server can record which session sent which encrypted ballot; once the ballot key is published (always the case for a decision that changes dues, rules or roles) that reveals how each person voted. Fixing that needs an anonymous channel (a mix network or blind signatures), which this project does not have. Against an unmodified server, a copy of the database shows no voter reference, no timestamp and, because every cast re-shuffles the rows, no cast order. Backups taken before a cast still hold the earlier layout.
- **What a recount proves.** A member's browser can check that the published counts match the ballots stored on the server, and that the member's own receipt is among the receipts. It cannot detect a ballot that was replaced before the key was published: receipts are random codes, not tied to a ballot. That is deliberate (a receipt that identified a ballot would let people prove how they voted to whoever pressures them), but it means the count is only as trustworthy as the server's ballot table. The server does check the ballots and receipts against the number of members who voted.
- **Key custody.** The ballot key is generated in the browser of whoever opens the vote and is split among the committee; that browser holds the whole key at that moment. "Nobody holds the key" means it is never stored whole.
- **Coercion.** Once the key is published, anyone who kept a copy of their own encrypted ballot, or whose device or connection was watched while voting, can show how they voted. For votes where that matters (a strike authorization, say) the committee can leave the key unpublished; the result then carries k committee signatures instead of a recount.
- **Membership is only as good as the identity checks around it.** Whoever generates the claim links can claim any account not yet claimed, and vote as that member.

### Devices and keys

- **A member's sign-in is kept in the browser.** The member link's secret is stored unencrypted in the browser's local storage so a member can come back. Quick exit does not remove it; "Forget this device" does. Anyone who can use an unlocked device can open that member's page.
- **Other things stay in browser storage too:** trustee and workspace key files, and after a vote a receipt code, which shows that this device was used to vote (not how). Quick exit does not remove any of them, and "Forget this device" removes only the member sign-in.
- **Key files are cached in browser storage** (encrypted under the passphrase with Argon2id). A generated passphrase is about 46 bits; a chosen one has to be at least 14 characters and not an obvious pattern (repeated letters or words, a run like 12345), but there is no dictionary check, so it can still be weak. Someone who takes a phone can try guesses offline. Use a generated passphrase.
- **Signatures and encrypted fields.** A trustee's request signature covers the route, the campaign and the exact request body, so a party that can alter requests after they are signed (a TLS-terminating proxy, a hostile browser extension) cannot change what it does; it could still hold it back. Requests made with bearer tokens (signers, members, workspace sessions) are not signed at all. Encrypted workspace fields written since 30 September 2026 are bound to their column and their row, so a value moved to another person's record shows as unreadable instead of as theirs; values written before then are bound to their column only, until they are next saved (ledger entries never are, because they cannot be changed).
- **A copy of the workspace database** shows, even without the master key, everything except names, emails, phones, addresses and job titles, ledger and spending payees and memos (all encrypted at rest), and case content (end-to-end). That includes the union and employer names, shifts, locations, preferred language, membership status, join and claim times, roles and who assigned them, announcements, vote titles, options and results (and any published vote key), who voted (not how), petitions and their signers, ledger amounts, categories and dates, dues plans, who filed grievances, the article cited, the decision, step outcomes and dates, the audit log, and session times. The encrypted-at-rest fields are readable by the server (it must send mail and print notices), so an attacker who steals both the database and `WORKSPACE_MASTER_KEY` reads it.
- **Without `NODE_ENV=production`** (which `npm start` does not set) and without `WORKSPACE_MASTER_KEY`, a server listening only on the loopback address writes a development master key next to the database. A server listening on any other address refuses to start without `WORKSPACE_MASTER_KEY`. On a real server, set both.

### Legal deadlines and content

- **Deadlines are reminders, not legal deadlines.** A case's clock starts when the case is filed and each later step's clock when someone records the step, not from the incident or from the employer's answer, so the app's due dates can be later than the contract's or the law's. Have a person check every date against the contract. (An explicit start date for each step is an open issue.)
- **Legal text is a draft.** Nothing here is legal advice, and no lawyer has reviewed it.
- **Once names go to an employer or an agency they are no longer secret.** The encryption protects the organizing period.

### Smaller points

- **Small unions:** with very few members, counts and shifts are inherently identifying; groups of fewer than 5 are hidden, and when only one would be hidden the next smallest is hidden with it, so the totals cannot give it away by subtraction. Within a group that is shown, a very small number of non-members (say 1 of 6) can still point at someone; that is not suppressed yet.
- The spreadsheet exports neutralise formula injection, and PDFs replace characters the standard fonts cannot draw with `?` (the CSV keeps full Unicode).
- **Not independently audited.**
